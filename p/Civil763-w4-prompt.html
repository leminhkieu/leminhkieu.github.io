Principles of Prompt Engineering

Brief it

1. Be clear and specific

2. Give it context to work with

3. Use technical terminology accurately

4. Structure the request around the coding task

Work with it

5. Ask for options before you ask for code

6. Remember the training cutoff

Check it

7. Double-check the outputs

The first four are about the brief you write. The last three are about how you behave once the code comes back. Most marks are lost in the last three.

What has changed

The models now read your files, run your code, search the web, and hold a whole project in memory while they work.

So the old game of hunting for magic words is over. Two things decide what you get back:

How well you brief it — the data, the constraints, the definition of done.

How hard you check it — a wrong answer arrives looking exactly like a right one.

A model that can run your code can also test it. Ask it to.

Practical consequence: upload the actual file, don't describe it. Paste the whole traceback, not the last line. The context window is large enough now that trimming costs you more than it saves.

1. Be clear and specific

Bad prompt:

"Generate code for a simulation."

Good prompt:

"I am building a traffic flow simulation in Python using discrete-event principles. Write a class IntersectionSimulator for a four-arm intersection with fixed-time signals. Inputs: arrival rate per approach in vehicles per hour, green time per approach in seconds, and cycle length. It should run for a set number of cycles and return the average delay per approach in seconds. Assume Poisson arrivals. Standard library plus NumPy only."

Say what the code takes in, what it gives back, and what it may depend on.

Vague in, plausible out. The model will not stop to ask what you meant unless you tell it to. Add "ask me anything ambiguous before you write code" and watch how much it actually wanted to know.

2. Give it context to work with

The model knows Python. It knows nothing about your file, your marking rubric, or the trap on line 40.

Bad prompt:

"Write code to get the data out of a file with pandas or something."

Good prompt — attach the file, then say:

"Attached is counts.csv: hourly vehicle counts at one intersection approach, one row per hour, columns date, hour, count. Hours with no working detector are recorded as the text 'n/a', not as blanks. Load it into pandas, convert count to a number, and tell me how many hours are missing per day before you do anything else."

Context is the part only you can supply. Everything else it can work out.

Worth demonstrating live. Without the warning about 'n/a', the count column loads as text, the mean silently fails or comes back wrong, and nothing raises an error. This slide previously carried a calculate_stats example, which was really about specificity, not context.

3. Use technical terminology accurately

The wrong word sends the model down the wrong road, confidently.

Loose:

"Group the counts and match them to the sites."

Precise:

"Aggregate counts.csv by date to get a daily total, then left join sites.csv on site_id to add the site name. Keep every date, even those with no matching site record — I want to see the gaps, not lose them."

Names carry meaning: left join, aggregate, resample, saturation flow, 95th percentile. Use them properly and you get the analysis you asked for.

"Group" could mean groupby, clustering, or binning. An inner join instead of a left join quietly drops rows, and the result still looks reasonable, so nobody notices. This is the most common invisible error in student code.

4. Structure the request around the coding task

Debugging: paste the full traceback, the code that produced it, the input that triggered it, and what you expected instead. Ask for the cause before the fix.

Optimisation: state the current runtime, the data size, and the target. Say what you cannot change.

Documentation: name the style and the audience.

Bad prompt:

"Fix my code."

Good prompt:

"This should return 24 rows, one per hour, but returns 26. Code and full traceback below; the input file has two duplicate timestamps. Explain what is causing the duplication before you change anything, then show the minimal fix and a check I can run to confirm the row count."

"Explain the cause before you change anything" is the highest-value habit on this slide. Otherwise you get a fix that makes the symptom disappear and the fault stay.

5. Ask for options before you ask for code

The first answer is the most obvious answer, not the best one. Make it show you the field before it commits.

"My hourly count data has gaps where the detector failed. Give me three defensible ways to handle them — do not write code yet. For each: the assumption behind it, what it does to my daily totals, and how I would justify it in a report. Then tell me which you would choose and why."

Then pick one, tell it which, and ask for the code.

Also worth asking: "What would you do differently if this had to run on a year of data from fifty sites?"

This is what separates using AI as a search engine from using it as a colleague. Three options with trade-offs force the assumption into the open, where it can be defended or attacked. A single unlabelled assumption buried in code is how an analysis quietly goes wrong.

6. Remember the training cutoff

Every model was trained up to a date and then stopped. It does not feel that gap, and it will answer anyway.

Libraries move: code written from memory still calls DataFrame.append(), removed in pandas 2.0.

Standards, design guides, prices and regulations move faster than any training run. A confident quote with no source is a guess.

What to do:

Attach the current document rather than asking it to recall what is in it.

Turn on web search for anything with a date on it, then check the source it cites — not just that it cited one.

Tell it which Python and library versions you are running.

Good live demo: ask for a figure from a standard or a current regulation without giving it the document, then attach the document and ask again. The tone of the two answers is identical. That is the lesson.

7. Double-check the outputs

Code that runs is not code that is right. Every number you hand in is yours, not the model's.

Cheap checks that catch most of it:

Count rows before and after every merge, and say out loud what the count should be.

Count missing values per column immediately after loading.

Hand-calculate one row end to end on a calculator, then find it in the output.

Plot the result. Wrong answers usually look wrong.

Then hand it back: "Here is your code and my result. What would make this wrong? List the assumptions you made that I did not ask for."

The hand-calculation is non-negotiable. One row, one calculation. It catches unit errors — seconds versus minutes, per hour versus per day — in every cohort. A model asked to review its own work will often find its own error, but only if you ask.

Putting it together

"Attached: counts.csv, hourly vehicle counts at one approach, columns date, hour, count. Goal: a table of daily totals and the morning peak hour for each day.

Context: missing hours are stored as the text 'n/a'. Some days are incomplete. Peak hour means the highest single hour between 06:00 and 10:00.

Before writing code: list the assumptions this task forces me to make and give me two or three options for each, with the effect on the daily totals.

Then: the loading code with a missing-value report, and three checks I can run to prove the totals are right.

I am on Python 3.12 and pandas 2.x. Ask me anything unclear before you start."

Walk through which principle each paragraph is doing: context, specificity, options, structure, verification, versions, and an invitation to ask questions. Two minutes to write, saves an afternoon.

When to stop trusting it

Warning signs, in the code and in the conversation:

A function or argument you cannot find in the library documentation.

A figure, threshold or standard quoted without a source.

Column names that do not exist in your file, invented to make the code look finished.

Row counts, totals or means that changed and were not mentioned.

Agreement the instant you push back. Real answers survive one challenge; invented ones fold immediately.

None of these come with an error message. That is the point.

Demonstrate the last one: challenge an answer you know is correct and see whether the model holds its ground. If it capitulates on something right, discount its confidence everywhere else in that conversation.

General tips

Give it the current code, not a description of the current code.

Break big problems into stages and check each one before moving on.

Use it to plan the analysis before you use it to write the analysis.

Ask it to explain its reasoning, then judge the reasoning, not the fluency.

Start a fresh conversation when the thread goes off the rails. Errors compound.

Keep a record of what you asked and what you accepted. That is your method section.

The last one matters for assessment. If you cannot explain why the code does what it does, you cannot defend the number, and the number is what is being marked.

How to Stay Current with LLM Capabilities

Experimenting with the latest models

Follow key information sources: websites of major AI labs, Huggingface, CivitAI, r/MachineLearning and r/LearnProgramming subreddits

Participate in the feedback loop

Refining and improving generated code

Pay attention to limitations that get resolved

Balancing AI Assistance with Core Programming Knowledge

Practice the 'understanding first' principle.

Implement a 'no-LLM day' in your weekly routine.

Use LLMs as tuitors, not just tools.

Challenge yourself with problems at the edge of your abilities

Remember that the meta-skill of knowing when and how to use AI is becoming as important as coding itself
